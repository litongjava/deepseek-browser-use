# 网页数据优先取文本（别读图）

这份手册是一次真实任务的复盘教训：任务是「看两只股票今天涨了还是跌了」，**数字早就全在 DOM 里**，
但我在过程中读了 3 张截图，其中一次还把图上的数字**读错了**（图上一条订单线读成 224.43，实际是 206.45，
靠后面的文本读数才纠正）。用户随后直接问：「你得出这个数据是不是用了视觉模式？」——这个问题本身就是结论。

## 一、一条判据：文本能表达的东西，永远不要用像素去取

| 你要的东西 | 首选来源 | 不要用 |
| --- | --- | --- |
| 数字、金额、涨跌幅 | 承载它的那个元素的 `innerText` / 页面标题 | 整页截图 + 视觉 |
| 表格一行行数据 | 表格行（`tr` / `[role=row]`）的文本 | 截图 |
| 「现在是涨还是跌」 | **收盘 vs 前收** 的数值比较 | **颜色**（红绿是用户配色，可改、且中西相反） |
| 当前状态、时间戳 | 状态字段、详情面板、`document.title` | 截图 |
| 接口里的原始值 | XHR 响应（服务端已缓存响应体，可直接读） | 页面渲染结果 |

三个理由，按重要性排：

1. **准确**：文本是页面自己渲染出来的值；视觉是「我看了一眼猜的」。上表里那次读错的正是视觉。
2. **便宜**：一次全页图进上下文的代价比同一次返回的文本高几个数量级，而**图不会多给一个字段**。
3. **可校验**：文本能拿两个独立来源对（见第三节），像素不能。

## 二、文本来源的优先次序（照这个顺序找，找到了就停）

1. **数据本身所在的元素**：有 `data-qa-id` / 稳定的 `aria-label` / 语义类名的容器最优先（例如行情图的
   图例 `[data-qa-id="legend"]`）。注意它可能是**实时更新**的，读到的就是那一刻的值。
2. **页面标题 `document.title`**：很多站点把「名称 + 最新值 + 涨跌幅」写进标题，一行就够。
3. **详情 / 侧栏面板**：同一份数据往往在主区和侧栏各渲染一次，侧栏那份常带「最后更新时间」。
4. **表格行文本**：一次取整块（例如面板容器）的 `innerText`，再在本地切分成行，比逐格点击便宜得多。
5. **XHR 响应**：上面的都不好用（数字在 canvas 里、或被前端算过），就回看接口响应——服务端保留最近若干条，
   「收到之后再跳走也能读」。
6. **像素（截图 / OCR）**：**最后手段**。只有「图上的东西根本没有文字形态」时才用，并且优先只截那一个元素。

### 例外：内容**本身**就是一张图时，读图才是第一条路

上面这条次序有个明确的反面，别把它套错场合：**当页面上的内容本身就是一张图片时，读图不是"最后手段"，而是唯一手段。**

典型：政府公告的附件（建设用地明细表、批复扫描件）、票据、合同扫描页、以图片形式发布的成绩单/公示。这些内容在 DOM 里只有一个 `<img>`，`innerText` 一个字都读不到 —— 此时第 1～5 条**全部无效**，再怎么换选择器、重取快照都是白跑。

**怎么在第一时间认出来**：

- `get_browser_state` 回执里的 `mediaCount` / `mediaHint` —— 非空就说明这页有大图（≥120×120 且面积 ≥4 万像素），提示里直接写了下一步；
- 或者：正文里明明在说「详见附件/见下图」，而你要的数字在文本里怎么搜都没有。

**正解**：

```text
download_image（取原始文件，拿到服务端 path）
  → ocr_image -p path=…（读文字；表格通常是 HTML/Markdown 形式）
  → 结果太长就 find_text 只取关心的几行
```

两条细节：**要的是原始文件而不是屏幕截图**（扫描件截屏再 OCR 会明显掉字）；整页扫描件、表格截图这类**文档级**识别，把 OCR 后端换成外部文档 OCR 工具（`browser.ocr.engine=command`），系统自带的 `Windows.Media.Ocr` 只擅长验证码那种短文本。

判断顺序可以压成一句话：**先问"这些字是不是根本不在 DOM 里"，再谈读不读图。** 在 DOM 里 —— 读文本；不在 DOM 里 —— 读图，而且要找原件。


## 三、交叉校验：两个独立来源对得上，才把它当结论

同一份数据通常在页面上有两个来源。**别嫌麻烦，对一遍**，这是「读文本」相对「读图」的真正优势：

- 持仓表里的「市值 / 盈亏」与资产汇总里的「证券市值 / 未实现盈亏」应当**加得起来**；
- 图表图例的 `涨跌幅` 与 `前收 × (1 + 幅度) == 收盘` 应当自洽（前收常能从同一行的买一 / 卖一倒算）；
- 接口响应里的数字与页面上渲染的数字应当一致。

实测就有一次：面板顶部资产数字与「证券市值 + 现金」差了 3.03 —— 不是数据错，是**同一屏里两处来自不同刷新瞬间**。
这类差异靠视觉是看不出来的，靠「我知道这两处该相等，且它们差得不合理」才能发现。

## 四、时间基准：先确认「这个数是哪一刻的」

数字对，但**时间基准错**，结论照样是错的。踩过的具体案例：任务是「今天涨了还是跌了」，
而那天是**周日（美股休市）**，图上最后一根是**周五**的 K 线。差一步就把周五的涨跌说成「今天」。

所以读任何时间敏感数据之前，先固定三件事：

1. **页面最后更新时间**（面板/详情里通常写着 `Last update at …`）；
2. **你自己机器的当前时间**（`new Date()`，注意时区偏移）；
3. **该市场/该业务当时是否在开市/服务状态中**（休市日 → 上一根就是上一个交易日）。

三者摆齐再解释数据；「今天」「当天的」这类词能不用就不用，直接写清具体日期。

## 五、canvas 上的东西读不到——这不是选择器错了

图表、地图、看板里的**刻度、坐标轴、十字线浮标**是画在 `<canvas>` 上的**像素**，而且 canvas 通常
**不进快照**（不可交互 → 没有索引）。所以：

- `innerText` 必然为空，`get_element_text` 按索引也够不着它（没索引）；
- 诊断用 `get_element_text` 传 `selector` + `canvasOnly:true`：它会回 `canvasOnly:true` 与 `hint`，
  明确告诉你「不是选择器写错、也不是没加载完」；
- 从 canvas 上取值的两条正路：① 读**同一页面上同时是 DOM 文字**的地方（图例、数据面板、工具栏）；
  ② 用鼠标与页面交互后读文本（例如图表「按住」某一点，图例就变成那一点的数值）；
- 只有这两条都不成立，才 `screenshot` / `get_element_screenshot` + `ocr_image`。

## 六、如果确实必须看图：把成本压到最低

- **只截那一个元素**（`get_element_screenshot` 传 `index` 或 `selector`），不要整页；
- 一次任务里**最多读一张**，并优先让服务端 OCR（`ocr_image`）而不是把图交给视觉模型；
- 读之前先问一句：「这个信息有没有文本形态？」——有就先取文本，图留作**取证截图**（给人看、存档），
  不为了填自己的结论去读它；
- 记住自动截图是**每条变化命令都会产生**的：它们的路径可以顺手记下来备用，但**不要顺手读进上下文**。

## 七、这次任务的账，作为成本参照

| 读图次数 | 目的 | 净收获 |
| --- | --- | --- |
| 第 1 张（全页） | 想读十字线浮标上的日期 | **没读到**（那是 canvas）；顺带读到的订单线价格还**读错了** |
| 第 2 张（全页） | 同上 | 位置感，数字文本里全都有 → **≈0** |
| 第 3 张（区域特写） | 同上 | 裁剪区里根本没有时间轴 → **0** |

最后定稿的表格里，**没有一个数字来自读图**：全部来自图例文本、页面标题、持仓表行文本、订单表文本与系统时钟。
日期这个唯一真的只有像素的地方，最后是用「详情面板的更新时间 + 系统时钟」推出来的。

**结论：先穷尽 DOM，再考虑像素；读不到就说读不到，并换判据，而不是去读整页大图。**
